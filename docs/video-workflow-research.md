## 0. 摘要

本报告回答一个问题：**视频工作流到底是怎么"跑起来"的？**

把国内外 66 个应用与项目拆到执行模型这一层之后，会发现它们的差异不在"有没有 AI",而在**四个结构性选择**：

1. **谁描述流程**——人画图（节点式）、人写代码（声明式）、模型自己规划（Agent 式）、厂商写死（黑盒式）。
2. **谁执行流程**——本地推理引擎、浏览器渲染、云端渲染农场、模型服务商的推理集群。
3. **流程的最小可复用单元是什么**——节点图、组件树、JSON 时间线、模板、提示词。
4. **状态在哪里**——内存图、项目文件、对象存储、供应商数据库。

这四个选择组合出六种稳定的架构范式，本报告称之为 P1–P6。绝大多数产品是这六种范式的单体实现或混合体，没有第七种。

**三条主要结论：**

- **结论一：开源生态的重心已经从"模型"转移到"工作流引擎"。** ComfyUI 以 145,278 stars 成为整个视觉生成领域的实际标准运行时（GitHub API 实测），围绕它的工作流自动生成已成独立研究方向——本次检索到 ComfyUI-Copilot、ComfyUI-R1、ComfySearch、ComfyGPT、Well-Typed ComfyUI 五篇论文（arXiv API 实测）。而单模型仓库（Wan2.2 18,403 stars、HunyuanVideo 12,733 stars）已退居"节点供应商"位置。
- **结论二：国内与国外的分野不在能力，在交付形态。** 国内厂商强于"模型 + 一站式创作台"的纵向整合（可灵、即梦、万相、海螺均为单一入口覆盖生成到成片），国外厂商强于"工作流即产品"的横向解耦（Shotstack、Creatomate、fal.ai、Replicate 把渲染和推理做成 API，Remotion 把视频做成 React 组件）。前者优化**创作者上手时间**，后者优化**工程可集成性**。
- **结论三：视频工作流的真实瓶颈是可复现性，不是生成质量。** 一个 30 节点的 ComfyUI 工作流涉及 5 个模型、3 个自定义节点、若干随机种子；一次云 API 渲染涉及版本化模板与依赖镜像。当生成质量普遍越过"可用线"之后，决定生产可用性的是**同输入同输出**能力。这也是学术界开始给工作流图做类型系统的原因（Well-Typed ComfyUI, arXiv:2610.37673）。

**给不同读者的最短路径：**

| 你的身份 | 直接读 | 关键判断 |
|---|---|---|
| 产品/创业者 | §3、§4、§5 | 选范式比选模型重要；同范式内差异化靠垂直场景 |
| 架构师/工程师 | §2、§7、§8 | P1 与 P2 的可复现性差一个数量级，选型前先定这个 |
| 创作者 | §3.1、§4.1、§9 | 一站式平台省时间，节点式平台省成本但吃学习曲线 |
| 研究者 | §6 | 工作流自动生成、可控性、长视频一致性是三条主线 |

## 1. 研究口径与方法

### 1.1 "视频工作流"的定义边界

"视频工作流"在日常语境中至少指三种不同的东西，本报告把三者都纳入，但分别标注：

- **W1｜生成工作流**：从文本/图像/视频条件出发，经多个模型与后处理步骤，产出一段（或一批）视频片段。典型：ComfyUI 的 Wan2.2 图、可灵的"文生视频 → 首尾帧 → 延长"链路。
- **W2｜编辑工作流**：对已有素材做剪辑、转写、翻译、配音、合成、渲染。典型：剪映多轨道时间线、VideoLingo 字幕流水线、FFmpeg filtergraph。
- **W3｜生产工作流**：把 W1 与 W2 串成可批量、可调度、可发布的流水线。典型：MoneyPrinterTurbo 一键成片、Creatomate 的模板 API、n8n 编排。

三者的技术栈差异很大：W1 的核心是**推理调度与显存管理**，W2 的核心是**时间线与合成管线**，W3 的核心是**任务编排与幂等**。把它们混为一谈是多数"AI 视频工具"评测失真的原因。

## 2. 视频工作流的技术范式：六种执行模型

这一章是整份报告的分析骨架。后面所有产品的描述，最终都会落回这里的某一格。

### 2.1 P1｜节点图 / DAG 式（Node-Graph）

**核心思想**：把每个计算步骤抽象成一个节点，节点间的数据依赖构成有向无环图，引擎按拓扑序求值。

**代表**：ComfyUI、LiblibAI（在线 ComfyUI）、InvokeAI（图式工作流）、Blender 的几何节点/合成节点、Nuke。

**架构剖面**（以 ComfyUI 为标准样本）：

```
工作流 JSON（节点 + 边 + widgets_values）
        │
        ▼
   [ 前端画布 ]  ←→  [ 图编辑器 / 节点注册表 ]
        │
        ▼  POST /prompt
   [ 执行引擎 ]  ── 拓扑排序 → 缓存查表 → 逐节点调度
        │
        ├── 模型加载器节点（VAE / UNet / CLIP / LoRA）
        ├── 条件编码节点（prompt → embedding）
        ├── 采样器节点（KSampler，steps/cfg/seed/sampler_name）
        ├── 视频相关节点（帧插值、切片、VideoHelperSuite 的 VHS_LoadVideo）
        └── 后处理节点（解码、合成、保存）
        │
        ▼
   [ 输出目录 ]  +  [ 节点级缓存命中记录 ]
```

**为什么这个范式赢了图像/视频生成领域：**

1. **显存友好**。节点级求值允许"用完即卸"——采样完把 UNet 释放，再加载 VAE。这是 8GB 显卡能跑 14B 视频模型的关键，端到端 API 做不到。
2. **组合爆炸的成本低**。加一个新模型 = 写一个节点类，不改引擎。ComfyUI 的生态规模（145,278 stars，2026-11-06 实测）来自这个扩展性。
3. **中间结果可见**。每个节点的输出可预览、可局部重跑。这对调试生成链路是决定性的——你不知道第 3 步的 latent 长什么样，就没法调。

**代价：**

- **可复现性脆弱**。工作流依赖外部节点包版本、模型文件哈希、CUDA/cuDNN 版本。同一个 JSON 在两个环境跑出不同结果非常常见。这是 §6 那批"给工作流做类型系统"论文的问题起点。
- **学习曲线陡**。节点图对非程序员不友好，LiblibAI 之类平台把它包装成"在线工作流"就是在降低这一层门槛。
- **不适合线性时间线编辑**。节点图表达"素材 A 在 3.2 秒插入"很别扭；这是 P1 与 P2 的分界。

**边界**：单机显存、单次图求值时长、节点生态的供应链安全（自定义节点可执行任意 Python）。

### 2.2 P2｜代码声明式 / 程序化渲染（Programmatic）

**核心思想**：用代码描述视频，渲染器把代码求值成一帧帧图像。

**代表与语言实测**：

| 项目 | 实现语言（GitHub 实测） | 描述方式 | Stars |
|---|---|---|---|
| Remotion | TypeScript | React 组件树 = 视频帧 | 71,108 |
| Motion Canvas | TypeScript | Generator 函数 + 场景图 | 19,710 |
| Editly | TypeScript | JSON/JS 时间线 DSL | 5,583 |
| MoviePy | Python | Python 对象组合 | 15,117 |
| FFmpeg | C | filtergraph 字符串 | 66,576 |

**架构剖面（Remotion 式）**：

```
React 组件树
    │  <Composition id durationInFrames fps width height />
    ▼
[ 组件求值 ] --useCurrentFrame()--> 第 N 帧的虚拟 DOM
    │
    ▼
[ 无头浏览器渲染 ] 每帧一次截图（或 Canvas/WebGL 直出）
    │
    ▼
[ FFmpeg 编码 ] 帧序列 → H.264/H.265 + 音轨复用
```

**这个范式的独特价值**：**视频成为可版本控制、可测试、可 CI 的产物**。

- 视频参数是变量 → 批量生成 1000 个不同文案的视频 = 跑一次循环。
- 渲染是纯函数 → 可以单元测试"第 42 帧的标题文字是什么"。
- 依赖是 npm 包 → lockfile 天然带来可复现性。

这是 P1 做不到的：节点图 JSON 有版本但没依赖锁，而 `package-lock.json` 有。

**FFmpeg 是这一族的"汇编语言"**：filtergraph（`[0:v]scale=1280:720[a];[a][1:v]overlay[b]`）本质是一个文本表达的 DAG，被 libavfilter 解析执行。所有上层工具（Remotion、Editly、MoviePy、剪映导出）最终都落到它。66,576 stars 的 C 项目是整个视频工业的地基。

**边界**：浏览器渲染的吞吐（每帧一次布局+绘制）、字体与硬件编解码的确定性、复杂 3D 的缺失（需引入 WebGL/Three.js）。

### 2.3 P3｜云渲染 API / JSON 描述式（Render-as-a-Service）

**核心思想**：把 P2 的渲染器搬到云上，用 JSON 描述时间线，HTTP 提交，webhook 回调。

**代表（官网 meta 实测）**：

- **Shotstack**——"The Cloud Video Editing API"
- **Creatomate**——"API for generating and automating videos using no-code or code with Zapier, Make.com, n8n, Node.js, PHP, Ruby, Python, and others"
- **JSON2Video**——[B] 同类，JSON 描述场景
- **Plainly / Nexrender**——[B] After Effects 模板农场

**架构剖面**：

```
客户端 JSON（timeline: tracks[] → clips[] → asset/elements[]）
        │  POST /render
        ▼
[ API 网关 ] → [ 任务队列 ] → [ 渲染工作池 ]（FFmpeg / AE / 浏览器）
        │                              │
        │                              ├── 素材拉取（S3/URL）
        │                              ├── 字体与模板加载
        │                              └── 编码 + 上传
        ▼                              ▼
   返回 renderId  ←──── webhook / 轮询 ────  输出 URL
```

**这个范式的商业逻辑**：卖的不是模型，是**"渲染"这个动作的确定性 SLA**。客户是开发者与自动化流程（Creatomate 官网明确列出 Zapier/Make/n8n 集成），不是创作者。

**边界**：无状态单次渲染 → 不适合交互式编辑；成本随渲染分钟线性增长；模板能力受限于供应商实现的元素类型。

### 2.4 P4｜Agent / 自动化编排式

**核心思想**：由 LLM 或规则引擎规划步骤，调用多个工具（搜索、TTS、素材库、生成模型、剪辑器）完成任务。

**代表**：

- **n8n**（209,665 stars，TypeScript）——通用工作流自动化，视频流水线只是其一个应用场景
- **MoneyPrinterTurbo**（139,898 stars，Python）——"利用 AI 大模型和自动化工作流，根据主题或关键词一键生成高清短视频"（GitHub description 原文）
- **ShortGPT**（8,113 stars，Python）——"Experimental AI framework for youtube shorts / tiktok channel automation"
- **Pictory**——"Pictory's AI video agent plans the scenes, you review and refine"（官网 meta 原文）
- **Higgsfield**——"automate creative workflows with its AI agent"（官网 meta 原文）

**架构剖面（MoneyPrinterTurbo 式，开源可读）**：

```
主题关键词
   │
   ├─→ LLM 生成文案（script）
   ├─→ LLM 生成关键词 → 素材库检索/Pexels API 下载视频片段
   ├─→ TTS 合成旁白（Azure / Edge-TTS / gTTS 可选）
   ├─→ 字幕生成（对齐）
   └─→ FFmpeg 合成：拼接 + 音轨 + 字幕烧录 + BGM
   │
   ▼
 成片 mp4 + 发布元数据
```

这是一个**没有扩散模型**的视频工作流——它的全部"AI"在文案与素材检索，渲染完全靠 FFmpeg。这一点极重要：它说明**短视频自动化的瓶颈从来不是生成质量，是选题与素材匹配**。

**边界**：素材版权（依赖 Pexels 等免费库）、成片同质化、LLM 输出的不确定性破坏流程幂等。

### 2.5 P5｜端到端模型黑盒（Model-as-Product）

**核心思想**：一个提示词进，一段视频出，中间过程不可见、不可调。

**代表**：Sora、可灵、Vidu、PixVerse、海螺、通义万相、Runway Gen 系列、Pika、Luma、Veo、Wan/HunyuanVideo 的官方推理服务。

**架构剖面**（公开信息可推断的部分，标 B）：

```
prompt + 参考图/首尾帧
    │
    ▼
[ 前置安全审核 ]（文本 + 图像，多数地区强制）
    │
    ▼
[ 提示词改写 / 结构化 ]（LLM 扩写为镜头语言）
    │
    ▼
[ 视频 DiT 推理 ]（含 VAE 解码）
    │  ← 这里可能有负向提示、CFG、步数、种子，但用户通常只能调少部分
    ▼
[ 后处理 ]（超分、帧插值、水印、编码）
    │
    ▼
输出片段（通常数秒）
```

**用户的真实可控面**：提示词、参考图、首尾帧、时长档位、分辨率档位、镜头运动、（部分产品）种子。**不可控面**：采样器、步数、CFG、latent 中间态、模型组合。

**这就是为什么"专业工作流"必然回归 P1/P2**：当创作者需要第 17 帧的某个物体消失，黑盒给不了这个杠杆。

**边界**：单次时长受显存与注意力复杂度约束（长视频要么分段生成后拼接，要么用自回归/流式架构）；一致性随镜头数衰减；审核策略不可协商。

### 2.6 P6｜模板 / 数字人播报式

**核心思想**：把视频生产收敛成"填表"——选模板、填文本、选数字人/音色，系统渲染。

**代表（官网 meta 实测）**：

- **Synthesia**——"#1 AI Video Platform for Business"
- **D-ID**——"The #1 Choice for AI Generated Video Creation Platform"
- **讯飞智作**——"AI虚拟数字人视频制作-一键创作口播视频-文字转视频-数字分身定制"
- **Fliki**——"Turn text, scripts, and blog posts into videos with 2,000+ AI voices in 80+ languages"
- **Pictory**——"Describe your video, or start from a script, URL, PowerPoint or audio"

**架构剖面**：

```
脚本/PPT/URL/音频
    │
    ├─→ 文本分镜
    ├─→ 数字人驱动（TTS 音素 → 口型 viseme → 表情/姿态）
    ├─→ 场景模板套用（背景、字幕条、Logo）
    └─→ 合成渲染
    ▼
批量输出（同一模板 × N 条脚本）
```

**商业本质**：**卖一致性，不卖创意**。企业培训视频需要 500 条、每条 3 分钟、口型准确、品牌统一——这正是通用视频模型做不好的事。

**边界**：创意上限低；数字人形象授权与肖像权；多语言配音的情感保真度。

### 2.7 六范式的对照表

| 维度 | P1 节点图 | P2 程序化 | P3 云渲染 API | P4 Agent 编排 | P5 端到端黑盒 | P6 模板播报 |
|---|---|---|---|---|---|---|
| 流程由谁描述 | 人画图 | 人写代码 | 人写 JSON | 模型/规则规划 | 厂商写死 | 厂商模板 |
| 执行位置 | 本地 GPU | 本地/CI/浏览器 | 云端渲染池 | 本地或云 | 厂商推理集群 | 厂商渲染池 |
| 最小复用单元 | 节点图 JSON | 组件/函数 | Timeline JSON | 流程定义 | 提示词 | 模板 + 脚本 |
| 可复现性 | 中（依赖生态） | 高（lockfile） | 高（版本化模板） | 低（LLM 非确定） | 低（厂商版本漂移） | 高 |
| 可控粒度 | 极细（latent 级） | 帧级 | 元素级 | 步骤级 | 片段级 | 字段级 |
| 上手成本 | 高 | 高（需编程） | 中（需 API） | 低 | 极低 | 极低 |
| 单位成本 | 电费 + 硬件折旧 | 电费/CI 分钟 | 按渲染分钟计费 | 混合 | 按生成次数计费 | 按席位/分钟计费 |
| 典型用户 | AI 画师、研究者 | 前端/全栈工程师 |  SaaS 开发者、自动化团队 | 自媒体矩阵运营 | 创意工作者、广告 | 企业 L&D、市场部 |
| 护城河 | 生态与节点数量 | 开发者体验 | SLA 与稳定性 | 场景 know-how | 模型质量 | 企业销售与合规 |

**一个反直觉的观察**：P5 看起来最"先进"，但它的用户留存最依赖模型版本迭代；P4 看起来最"土"（很多只是 FFmpeg + TTS），但它是唯一能规模化产出**可发布内容**的范式——因为发布需要的是稳定产出，不是惊艳单条。

#### 3.5.10 剪映生态 / 模板工作流 `[B]`

- 说明：剪映的"模板"本质是**社区分发的参数化工作流**——模板作者定义结构，用户注入素材。这是国内规模最大的 P6 实践，但因闭源无法验证内部实现，此处仅作为范式样本记录。

**国内小结**：33 个条目中，模型层 9 个、平台层 7 个、企业层 3 个、基建层 4 个、开源项目 10 个（合计 33，无重叠）。**结构性观察**：国内的模型层与平台层高度绑定（同一集团内闭环），开源项目则大量由大厂研究部门输出（阿里、腾讯、百度、智谱）。真正的独立创业公司集中在模型层（生数、爱诗、MiniMax）与开源工具层（MoneyPrinter 系、VideoLingo）。

## 4. 国外应用与项目图谱（39 个）

**分组逻辑**：国外生态的特征是**分层更细、单层更专**。同一个"视频工作流"需求，会被拆成模型 API / 渲染 API / 编辑器 / 自动化工具四类独立产品，通过标准接口组合。这与国内"一站式平台"的取向形成结构性对比。

### 4.5 开发者工具与渲染基础设施（9 个）

#### 4.5.1 Remotion

#### 4.5.2 Motion Canvas

#### 4.5.3 Editly

#### 4.5.4 MoviePy

- **硬数据** `[A]`：Python，15,117 stars，创建 2013-08-12，最近推送 2026-08-26。
- **官方描述** `[A]`："Video editing with Python."
- **架构**：Python 对象模型（Clip / VideoClip / AudioClip）+ 惰性求值 + 最终交 FFmpeg 写入；支持 numpy 帧级操作。
- **功能**：剪辑、拼接、特效、文字、音频、GIF、逐帧处理。

- **特点**：**它是"用 Python 处理视频"这件事的默认答案**，生态位类似 pandas 之于数据处理。**大量 AI 视频项目（含国内 MoneyPrinterTurbo 一类）的合成层就是 MoviePy 或直接 FFmpeg**。
- **范式**：P2。

#### 4.5.5 FFmpeg

- **硬数据** `[A]`：C，66,576 stars，创建 2011-04-14，最近推送 2026-11-06。
- **官方描述** `[A]`："Mirror of https://git.ffmpeg.org/ffmpeg.git."
- **架构**：libavformat（容器）/ libavcodec（编解码）/ libavfilter（滤镜图）/ libswscale（缩放）/ libswresample（重采样）。filtergraph 是文本 DAG，由 avfilter 解析执行。
- **功能**：几乎所有音视频格式的转码、剪辑、滤镜、合成、推流。
- **边界**：没有时间线概念（需上层封装）；filtergraph 可读性差；硬件编码器行为依平台而异。
- **目标人群**：所有做视频的人（作为底层依赖）。
- **实现语言**：C。
- **特点**：**它是整个视频工业的地基**——本报告中几乎每个工具最终都调用它。理解 filtergraph 就理解了 80% 视频工作流的执行层。
- **范式**：执行层（跨所有范式）。

#### 4.5.6 Shotstack

- **官方定位** `[A]`："Shotstack - The Cloud Video Editing API."
- **架构** `[A/B]`：JSON timeline（tracks → clips → assets）→ 云端渲染集群 → 输出 URL；提供模板、合并（merge）、转码、托管。支持 webhook 与 SDK（Node/Python/PHP 等）。
- **功能**：云渲染、模板、批量、转码、字幕、音频。
- **边界**：按渲染时长计费；元素类型受 API 能力限制；交互式编辑不适用。
- **目标人群**：SaaS 开发者、自动化平台（电商视频、社交批量）。
- **实现语言**：闭源（SDK 多语言）。
- **特点**：**"渲染即服务"的商业化样本**——客户不需要 GPU，只需要 HTTP。这是 P3 范式最清晰的形态。
- **范式**：P3。

#### 4.5.7 Creatomate

- **官方定位** `[A]`："Creatomate is an API for generating and automating videos using no-code or code with Zapier, Make.com, n8n, Node.js, PHP, Ruby, Python, and others."
- **架构** `[A/B]`：JSON 元素树（composition → elements）→ 云端渲染 → 输出；提供可视化模板编辑器（让非程序员改模板）。
- **功能**：模板渲染、批量生成、图片/视频/文字/音频元素、webhook、集成 Zapier/Make/n8n。
- **边界**：动画能力受模板系统限制；计费按输出时长。
- **目标人群**：自动化团队、营销技术（MarTech）、无代码用户。
- **实现语言**：闭源。
- **特点**：**官网把 n8n/Zapier/Make 写进第一句描述**，明确自己的定位是**自动化流水线里的一个节点**，而不是给人用的编辑器。这是 P3 与 P4 结合的典型。
- **范式**：P3。

#### 4.5.8 JSON2Video

- **定位** `[B]`：JSON 描述场景 → 云渲染 API，面向开发者与自动化。
- **架构** `[B]`：与 Shotstack/Creatomate 同构（JSON timeline → 渲染池 → URL）。
- **功能** `[B]`：场景渲染、元素动画、批量、集成。
- **边界** `[B]`：同 P3 通病。
- **目标人群**：开发者、自动化流程。
- **实现语言**：闭源。
- **特点**：**同质化竞争下的价格与集成之争**——P3 范式的技术门槛主要在"稳定渲染 + 低延迟队列"，不在功能列表。
- **范式**：P3。

#### 4.5.9 n8n

- **硬数据** `[A]`：TypeScript，209,665 stars（本次调研中 stars 最高的仓库），创建 2019-06-22，最近推送 2026-11-06。
- **官方描述** `[A]`："Fair-code workflow automation platform with native AI capabilities. Combine visual building with custom code, self-host or cloud, 400+ integrations."
- **架构**：节点式自动化引擎（**与 ComfyUI 同为节点图，但节点是"服务调用"而非"张量运算"**）+ 触发器（webhook/cron/事件）+ 执行历史 + 可自托管。
- **功能**：400+ 集成、可视化编排、代码节点、AI 节点、自托管、错误重试。
- **边界**：不擅长像素级媒体处理（需调 FFmpeg/云 API）；大规模并发需自建队列。
- **目标人群**：自动化工程师、运营技术、中小企业 IT。
- **实现语言**：TypeScript。
- **特点**：**它证明节点图范式不限于 AI**——把"节点"从算子抽象为 API 调用，就得到通用自动化平台。视频工作流在 n8n 里是"触发器 → 生成 API → 素材 → 渲染 API → 发布"的编排，其价值在**粘合**而非计算。
- **范式**：P4（通用编排）。

### 4.7 补充：ComfyUI 生态与视频节点（2 个）

#### 4.7.1 ComfyUI｜Comfy Org

- **硬数据** `[A]`：Python，145,278 stars，17,288 forks，创建 2023-01-17，最近推送 2026-11-06。
- **官方描述** `[A]`："The most powerful and modular diffusion model GUI, api and backend with a graph/nodes interface. The fastest local inference engine in the world."
- **架构**：① 前端画布（TypeScript/LiteGraph 风格）；② `/prompt` HTTP API 接收工作流 JSON；③ Python 执行引擎做拓扑排序 + 节点级缓存；④ 节点注册表支持第三方包；⑤ 模型管理（checkpoints/loras/vae 分类）。
- **功能**：图式生成、模型混合、视频工作流、API 服务化、自定义节点生态。

- **特点**：**它是本报告的核心参照物**——几乎所有开源视频模型（Wan、HunyuanVideo、CogVideoX、LTX-Video、Mochi、SVD）都以"提供 ComfyUI 节点"作为分发策略。谁被 ComfyUI 接纳，谁就进入全球工作流生态。
- **范式**：P1（标准实现）。

#### 4.7.2 ComfyUI-VideoHelperSuite

- **硬数据** `[A]`：Python，1,910 stars，创建 2023-09-23，最近推送 2026-09-02。
- **官方描述** `[A]`："Nodes related to video workflows."
- **架构** `[A/B]`：视频加载/保存/合成/帧操作节点集合，桥接图像生成生态与视频工作流。
- **特点**：**它揭示了一个关键事实**：ComfyUI 原生的图像中心设计并不直接支持视频，视频能力是靠这类"适配节点"补齐的。**生态的空白处会长出关键基础设施**——1,910 stars 的仓库支撑着 145,278 stars 平台的视频能力。
- **范式**：P1 生态组件。

**国外小结**：39 个条目中，模型层 7、编辑层 7、企业层 6、自动化层 4、开发者工具 9、开源模型 4、ComfyUI 生态 2（合计 39，无重叠）。**结构性观察**：国外生态把"渲染"（P3）、"编排"（P4）、"代码化"（P2）拆成独立产业，彼此通过 JSON/HTTP 组合；国内则倾向把三者收进一个产品。前者利于集成，后者利于转化。

## 6. 学术前沿：论文告诉我们的"工作方式"

本节所有论文均经 `export.arxiv.org/api` 实测检索获得（2026-11-06），标题与 arXiv ID 可直接复核。

### 6.1 控制与可控生成：从"抽卡"到"约束求解"

| 论文 | arXiv ID | 时间 | 核心命题 |
|---|---|---|---|
| Controllable Video Generation: A Survey | 2507.16869 | 2025-07 | 系统梳理可控性的维度：结构、运动、外观、相机、时序 |
| A Survey: Spatiotemporal Consistency in Video Generation | 2502.17863 | 2025-02 | 时空一致性是视频区别于图像的根本难题 |
| Human Motion Video Generation: A Survey | 2509.03883 | 2025-09 | 人物动作生成是短剧/数字人的技术底座 |

**对工作流的含义**：可控性研究把"控制"分解为**可独立施加的约束通道**（结构图、深度、姿态、光流、相机参数）。这直接对应 P1 节点图中的控制节点——每一个控制通道就是一个可插拔节点。**P1 之所以能成为专业工作流标准，是因为它的数据模型天然容纳多通道约束**；P5 黑盒只能在产品层暴露少数几个通道。

### 6.2 工作流自动生成：LLM 开始"画图"

这是最值得关注的新方向——**用模型生成工作流本身**：

| 论文 | arXiv ID | 时间 | 做的事 |
|---|---|---|---|
| ComfyUI-Copilot: An Intelligent Assistant for Automated Workflow Development | 2506.05010 | 2025-06 | 助手式地辅助构建 ComfyUI 工作流 |
| ComfyUI-R1: Exploring Reasoning Models for Workflow Generation | 2506.09790 | 2025-06 | 用推理模型直接从需求生成工作流图 |
| ComfyGPT: A Self-Optimizing Multi-Agent System for Comprehensive ComfyUI Workflow Generation | 2503.17671 | 2025-03 | 多 Agent 自我优化地生成工作流 |
| ComfySearch: Autonomous Exploration and Reasoning for ComfyUI Workflows | 2601.04060 | 2026-01 | 自主探索与推理搜索工作流空间 |
| **Well-Typed ComfyUI Cannot Go Wrong: Gradual Refinement Types for Generative-AI Workflow Graphs** | 2610.37673 | 2026-10 | **给工作流图做渐进式细化类型系统** |

**这五篇连起来是一条清晰的技术演进线：**

```
2025-03  多 Agent 生成工作流        （能生成，但正确性无保证）
2025-06  推理模型 + 助手辅助         （质量提升，仍靠试错）
2026-01  自主探索与搜索              （能搜索，但搜索空间爆炸）
2026-10  渐进式细化类型系统          （从"能生成"转向"可证明正确"）
```

**为什么类型系统是这条线的终点**：一个 ComfyUI 工作流是**带类型的图**——`LATENT` 不能直接连到 `IMAGE` 输入，`MODEL` 必须来自加载器。当 LLM 自动生成工作流时，最高效的约束不是"生成后试跑"，而是**在生成时就由类型系统排除非法图**。2610.37673 提出的渐进式细化类型（gradual refinement types）正是把"运行时会炸"提前到"类型检查会拒"。

**工程启示（可直接用于自建工作流引擎）**：

1. 定义节点端口的**类型 lattice**（IMAGE / LATENT / MASK / CONDITIONING / VIDEO / AUDIO），而不是用 `any`。
2. 边连接时做类型合一（unification），不合法即拒绝——这比运行时崩溃早一个数量级。
3. 类型可携带**细化谓词**（如 `LATENT[shape=(B,4,H/8,W/8)]`），让形状错误在编辑期暴露。
4. 有了类型，工作流的**自动补全与自动修复**才有可能——这是 Copilot 类功能的地基。

## 7. 架构模式提炼（工程视角）

这一节把前面 66 个样本压缩成可复用的设计判断。**如果你要自建视频工作流系统，这是最该读的一节。**

### 7.1 执行引擎的三层结构

所有成熟的工作流系统都能拆成这三层：

```
┌─────────────────────────────────────────────┐
│  L3  描述层（Description）                    │
│      节点图 JSON / React 组件 / Timeline JSON  │
│      / Python DSL / filtergraph 字符串         │
├─────────────────────────────────────────────┤
│  L2  调度层（Orchestration）                  │
│      拓扑排序 / 缓存查表 / 并发控制 / 重试      │
│      / 资源配额 / 进度上报                     │
├─────────────────────────────────────────────┤
│  L1  执行层（Execution）                      │
│      模型推理 / FFmpeg 调用 / 浏览器渲染       │
│      / 云端任务                             │
└─────────────────────────────────────────────┘
```

**样本对照**：

| 系统 | L3 | L2 | L1 |
|---|---|---|---|
| ComfyUI | 节点图 JSON | Python 执行引擎（拓扑序 + 节点缓存） | PyTorch 推理 |
| Remotion | React 组件树 | CLI 逐帧调度 | 无头浏览器 + FFmpeg |
| Shotstack | Timeline JSON | 云队列 | 渲染池 |
| n8n | 节点图（服务节点） | TS 工作流引擎 | HTTP 调用 |
| Editly | JSON clips | Node 调度 | FFmpeg filtergraph |
| MoviePy | Python 对象 | 惰性求值 | FFmpeg + numpy |

**设计判断**：**L2 是竞争壁垒所在，不是 L1**。L1 可以买（用现成模型、用 FFmpeg、用云渲染），L3 可以抄（JSON schema 大同小异），只有 L2 决定系统能不能扛住"30 节点 × 1000 次/天 × 失败重试"。

### 7.2 缓存：视频工作流的经济命脉

**为什么视频工作流比图像工作流更需要缓存**：一个 5 秒 720p 视频 = 120 帧，成本是单图的 100 倍以上。任何重复计算都是直接烧钱。

**ComfyUI 的节点级缓存**（最有参考价值的设计）：

- 每个节点的输出以 `(节点类型, 输入哈希, 参数哈希)` 为键缓存。
- 改动下游节点，上游不重算。
- 这使"调最后一个后处理节点"的成本从"重跑整个链路"降到"跑一个节点"。

**工程要点**：

1. **缓存键必须包含模型身份**（模型文件 hash + 版本），否则换模型后命中脏缓存。
2. **缓存要有 TTL 或容量上限**——视频中间产物体积巨大（一个 1080p 帧序列可达 GB 级）。
3. **分布式场景下缓存要内容寻址**（如 `sha256(输入+参数)`），不能依赖节点 ID。

### 7.3 可复现性：四个必须记录的维度

一个视频工作流要"同输入同输出"，必须固定四样东西：

| 维度 | 内容 | 不固定的后果 |
|---|---|---|
| **模型身份** | checkpoint hash、LoRA 版本、VAE 版本 | 换个 LoRA 文件，画面全变 |
| **计算图** | 节点图/代码的完整快照（含版本号） | 节点包升级导致行为变化 |
| **随机性** | seed、采样器、步数、CFG | 无法复现任何一次生成 |
| **环境** | CUDA/cuDNN 版本、依赖 lockfile、FFmpeg 版本 | 编码参数漂移、色彩偏移 |

**对照样本**：

- **Remotion**：天然满足后三项（package-lock + 纯函数 + 无随机），第一项靠模型文件管理。
- **ComfyUI**：四项都要人工管，这是它最大的工程债。
- **云渲染 API**：供应商替你固定环境（卖点之一），但模型版本仍可能静默更新。
- **黑盒 SaaS**：四项全不可控，这是 P5 的结构性缺陷。

**可操作建议**：给每个工作流产出一个 **manifest 文件**（模型 hash 列表 + 图快照 + 种子 + 环境指纹），与输出一起存储。这不难实现，但绝大多数团队没做——直到需要重跑三个月前的项目。

### 7.4 状态管理：三种合法选择

| 方案 | 代表 | 优点 | 代价 |
|---|---|---|---|
| **内存图 + 磁盘中间产物** | ComfyUI | 简单、调试友好 | 无法水平扩展，进程崩溃即丢失 |
| **工程文件 + 显式保存** | 剪映、Premiere、OpenShot | 用户可控、可版本化 | 需处理并发与冲突 |
| **无状态 + 对象存储** | Shotstack、Creatomate | 天然可扩展、幂等 | 不适合交互式编辑 |

**判断规则**：**交互式 → 工程文件；批处理 → 无状态**。试图用一套状态模型同时满足两者（例如让云 API 支持"实时编辑"）会付出巨大复杂度代价。

### 7.5 规模化的三个真实瓶颈

按出现频率排序：

1. **冷启动 / 模型加载**。一个 14B 视频模型从磁盘到显存需要数十秒。批处理场景下，把模型常驻（warm pool）比优化单次推理收益大得多。
2. **显存碎片与并发度**。视频模型显存占用大，并发数往往只能到 1–2。真正的吞吐提升来自**队列化 + 批内复用**（同一模型处理排队任务），而非并行。
3. **存储 I/O**。视频中间产物是 I/O 密集型负载，本地 NVMe 与网络存储的性能差可达 10 倍。多数"云端工作流慢"的根因在这里，不在 GPU。

### 7.6 成本结构对照

| 范式 | 主要成本项 | 边际成本特征 | 优化杠杆 |
|---|---|---|---|
| P1 本地 | 硬件折旧 + 电费 | 近乎零边际 | 模型量化、显存优化、缓存 |
| P2 程序化 | CI 分钟 / CPU | 线性 | 增量渲染、帧级缓存 |
| P3 云渲染 | 渲染分钟 | 线性 | 模板复用、分辨率档位 |
| P4 Agent | LLM tokens + 素材 + 渲染 | 线性（LLM 部分波动大） | 提示词缓存、结构化输出 |
| P5 黑盒 | 按次生成 | 线性且单价高 | 抽卡次数控制、参考图质量 |
| P6 模板 | 席位 / 分钟 | 线性 | 模板复用、批量折扣 |

**给决策者的判断**：日产量 < 50 条选 P5/P6（省人力），日产量 50–500 条选 P4（省重复劳动），日产量 > 500 条或需要极致定制选 P1/P2（省边际成本）。这是本报告最实用的一个结论。

## 8. 功能边界：技术约束如何决定产品形态

这一节讨论"为什么产品长成这样"——边界不是厂商的懒惰，多数是物理约束。

### 8.1 生成侧的五道硬边界

| 边界 | 物理原因 | 产品表现 | 谁在突破 |
|---|---|---|---|
| **时长** | 注意力复杂度随帧数平方增长；显存线性增长 | 单次 5–10 秒为主流，长视频靠分段 | SkyReels-V2（无限长度架构）、Sora（分段规划） |
| **一致性** | 无跨片段记忆机制 | 人物/场景在多镜头间漂移 | Vidu（主体参考）、Runway（Act-One） |
| **可控性** | 黑盒不暴露中间态 | 只能调提示词与少数参数 | ComfyUI（latent 级）、Runway（约束工具） |
| **确定性** | 扩散采样 + 环境差异 | 同提示词不同结果 | Remotion（无随机）、云 API（固定环境） |
| **物理合理性** | 训练数据缺乏物理标注 | 碰撞、液体、布料失真 | 世界模型方向（Sora/Veo 的叙事） |

**关键判断**：这五道边界里，**只有"确定性"是工程可解的**（靠架构选择），其余四项都需要模型进步。所以一个负责任的架构决策是：**先选一个确定性可达的范式（P2/P3），再在其上接入不确定的生成能力（P5）**——而不是反过来。

### 8.2 编辑侧的边界

| 边界 | 原因 | 表现 |
|---|---|---|
| 时间线复杂度 | UI 与数据的耦合 | 超过 100 轨/1000 片段后交互变慢 |
| 编解码格式 | 专利与硬件支持 | 部分格式需转码中转 |
| 色彩管理 | HDR/色彩空间传递链 | 跨工具往返后色偏 |
| 音频同步 | 采样率与时钟漂移 | 长项目音画不同步 |

**开源编辑器（OpenShot/Shotcut）与商业 NLE 的差距主要在第 2、3 项**——这是工程积累，不是算法。

### 8.3 合规与审核边界

| 类型 | 触发点 | 影响 |
|---|---|---|
| 内容审核（生成前） | 提示词/参考图 | 部分题材不可生成，且规则不透明 |
| 内容审核（生成后） | 输出帧 | 可能生成后被拦截，浪费算力 |
| 肖像权/声音权 | 数字人、声音克隆 | 需授权证明，企业采购的硬门槛 |
| 版权（训练数据） | 模型层面 | Adobe 用 Content Credentials 做差异化 |
| 平台条款 | 自动发布类工具 | MoneyPrinterPlus 类项目的高风险点 |
| 水印与标识 | 部分地区法规 | 输出强制标识，影响商用 |

**产品影响**：审核策略的严格程度直接决定产品可用场景。这也是为什么"同一个模型，国内版和国际版能力不同"——不是技术差异，是合规差异。

### 8.4 成本边界（决定商业模式）

- **P5 的定价必须覆盖"抽卡成本"**。用户平均生成 5 次才满意 1 次，那么单条可用视频的真实成本是标价的 5 倍。这解释了为什么多数 AI 视频产品采用积分制而非包月无限。
- **P1 的成本是硬件折旧**。本地跑 1000 条和 1 条的电费差异可忽略，但硬件一次性投入高。这决定了 P1 适合"高频重度用户"，不适合"偶尔用用"。
- **P2/P3 的成本是 CPU 时间**，比 GPU 便宜一个量级。这是程序化视频（Remotion/Creatomate）能做大宗业务的根本原因。

## 9. 目标人群分层与匹配

### 9.1 六类人群的需求差异

| 人群 | 核心诉求 | 容忍什么 | 不容忍什么 | 匹配范式 |
|---|---|---|---|---|
| **个人创作者** | 快速出片、零门槛 | 模板化、同质化 | 学习成本、付费门槛 | P5、P6 |
| **专业剪辑师** | 精细控制、稳定性 | 学习曲线 | 不可控、丢工程 | P2 |
| **AI 画师/研究者** | 极致控制、可实验 | 环境配置麻烦 | 能力天花板 | P1 |
| **自媒体矩阵** | 批量、低成本、可发布 | 质量中等 | 人工介入多 | P4 |
| **企业 L&D / 市场** | 一致、合规、可批量 | 创意平庸 | 合规风险、不可审计 | P6 |
| **开发者/ISV** | 可集成、可编排 | 需要自己写胶水 | 黑盒、无 API、锁死 | P2、P3、P4 |

### 9.2 一个被误判的人群：中小商家

电商/本地生活商家是最大的潜在市场，但**他们的真实需求不是"生成视频"，是"生成能带来转化的素材"**。这导致：

- 他们需要的不是 P5 的惊艳片段，而是**P4 的批量变体**（同一商品 × 10 个卖点 × 3 个平台）。
- 他们无法评估"生成质量"，只能评估"投放 ROI"。
- 因此面向他们的产品必须**绑定投放数据闭环**——这是纯生成工具做不了的事。

**这是一个结构性机会**：把视频工作流的终点从"导出"延伸到"投放效果回流"，让下一次生成的提示词由数据驱动。目前只有少数产品在做（Higgsfield 的广告定位接近）。

## 10. 选型建议

### 10.1 决策树

```
你要做什么？
│
├─ 每天需要 N 条标准化视频（培训/播报/商品）
│   └─→ P6 模板播报（Synthesia / 讯飞智作 / Fliki）
│       判断依据：一致性 > 创意
│
├─ 每天需要 N 条有创意的短视频（自媒体/带货）
│   └─→ P4 Agent 编排（MoneyPrinterTurbo / Pictory / InVideo）
│       判断依据：批量 > 单条质量
│
├─ 需要精细控制的成片（广告/短片/影视）
│   ├─ 有 GPU 和工程能力 → P1 节点图（ComfyUI + Wan/HunyuanVideo）
│   └─ 没有 → P5 黑盒（可灵/Runway/Vidu）+ 人工后期
│
├─ 需要把视频嵌入产品/系统
│   ├─ 前端团队 → P2 程序化（Remotion）
│   └─ 后端团队 → P3 云渲染（Shotstack/Creatomate）
│
└─ 需要把多个环节串起来（素材→生成→剪辑→发布）
    └─→ P4 通用编排（n8n + 各环节 API）
```

### 10.2 五条硬建议

1. **不要用 P5 做批量生产**。抽卡成本 + 不确定性会让单位成本失控。批量场景选 P4/P6。
2. **不要用 P1 做团队协作**。节点图 JSON 的合并冲突是灾难。要么单点负责制，要么用平台版（LiblibAI 类）。
3. **一定会遇到可复现性问题**。提前建 manifest 机制（模型 hash + 图快照 + 种子 + 环境指纹），成本很低，收益是"三个月后还能重跑"。
4. **把渲染和生成分开评估**。生成质量决定上限，渲染稳定性决定下限。多数项目失败在下限。
5. **先确定"终点"再选工具**。终点是"导出成片"还是"发布到平台"还是"投放并回流数据"？这三种终点对应完全不同的工具组合。

### 10.3 三个反模式

| 反模式 | 表现 | 后果 |
|---|---|---|
| 用聊天框代替工作流 | 反复提示词试错，无中间产物 | 无法定位问题、无法复用 |
| 用工作流代替创作判断 | 搭 100 个节点追求全自动 | 维护成本超过收益 |
| 用一个模型解决所有场景 | 培训、广告、短剧都用同一模型 | 每类场景都不达标 |

## 11. 趋势判断（基于本次数据的推断，标注置信度）

### 11.1 高置信度

**① 工作流引擎将成为独立品类。**
证据：ComfyUI 145,278 stars 高于任何单一视频模型仓库；围绕它的工作流自动生成已形成论文簇（5 篇，2025-03 至 2026-10）。判断：未来两年会出现"工作流层的标准协议"（类似 MLIR 之于编译器），让工作流在不同引擎间可移植。

**② 类型系统会进入工作流。**
证据：arXiv:2610.37673 已提出渐进式细化类型。判断：这是自动生成工作流的前置条件，一旦成熟会成为引擎标配。

**③ 国内厂商会继续"模型 + 平台"纵向整合，但开源会成为标配动作。**
证据：阿里（Wan2.1/2.2）、腾讯（HunyuanVideo）、智谱（CogVideo）、昆仑万维（SkyReels）均已开源主力模型；未开源的厂商在开发者心智上处于劣势。

### 11.2 中置信度

**④ 长视频会从"拼接"转向"架构级连续生成"。**
证据：SkyReels-V2 的 "Infinite-length" 与 arXiv 上长视频一致性研究的密度。判断：拼接方案会在 1–2 年内被视为落后工艺。

**⑤ 视频工作流的终点会从"成片"延伸到"分发 + 反馈"。**
证据：MoneyPrinterPlus 已实现自动发布；Higgsfield 主打广告工作流。判断：闭环数据会反过来决定生成参数，形成"投放驱动生成"。

### 11.3 低置信度（值得关注但证据不足）

**⑥ 实时生成会成为独立赛道。**
证据：Krea 的实时画布、PixVerse 官网提到"实时世界与互动娱乐"、LTX-Video 的少步数推理。判断：技术上可行性在提升，但商业模式不清晰（谁为实时付费？）。

**⑦ 3D 与视频工作流会合流。**
证据：Luma 同时具备视频生成与 3D 捕捉。判断：如果"从实拍到虚拟场景"成为主流工作流，两者必然合并；但目前需求尚未验证。
